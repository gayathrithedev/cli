PRODUCT GOAL

Entire Echo is for developers with dyslexia, ADHD, reading fatigue, or anyone
taking over AI-assisted work who needs to understand:

1. What was requested?
2. What was implemented?
3. What is missing or uncertain?
4. What could be affected?
5. How can the work be continued safely?

The current UI exposes these as one long technical document. Redesign it into a
guided review where the user always knows:

- where they are;
- what the current information means;
- how reliable the context is;
- what can be heard;
- where the supporting evidence lives;
- what to do next.

DESKTOP INFORMATION ARCHITECTURE

Build an app shell that works within a 13–14 inch laptop viewport:

1. TOP HEADER

   Approximately 64px tall.

   Left:
   - Entire Echo
   - concise text describing it as a checkpoint review

   Middle/right:
   - “Local-only”
   - context state: Complete, Partial, Redacted or Unavailable
   - Focused/Detailed control

   Context state must include visible text and must not rely only on color.

2. LEFT REVIEW NAVIGATION

   Four numbered interactive steps:

   1. Requested
   2. Implemented
   3. Missing or uncertain
   4. Potentially affected

   Each step shows a concise count or state:
   - “Unavailable”
   - “1 finding”
   - “4 potential impacts”

   Replace every “Make current card” button with understandable navigation.
   The navigation item itself selects the corresponding review section.

   Use buttons or correct tab semantics with:
   - aria-selected or aria-current
   - visible keyboard focus
   - predictable Tab navigation
   - optional ArrowUp/ArrowDown navigation only if implemented correctly

3. MAIN REVIEW PANEL

   Show only one active review section in Focused mode.

   The panel contains:

   - Current step and progress: “Step 2 of 4”
   - Plain-language section heading
   - One-sentence explanation of what this section means
   - Claims with confidence labels
   - “View supporting evidence” per claim
   - Collapsed “Technical details” disclosure for raw paths, symbols and
     commands

   Do not place a long file list in the primary reading text. Preserve it inside
   technical details and evidence.

   Do not fabricate a summary. Any simplified text must be a deterministic
   presentation of existing claims and context fields.

4. CONTEXT LIMITATION

   Replace the enormous yellow warning block with a compact context banner:

   “This review has redacted context”

   Supporting text:
   “Some checkpoint information was unavailable or redacted. Findings below
   are limited to the evidence that could be verified.”

   Provide a “Why is this incomplete?” disclosure containing every exact reason.

   Preserve every reason and warning. Change only presentation, not evidence.

5. CHECKPOINT METADATA

   Show checkpoint, session and commit as compact metadata.

   Use monospace text and truncate long identifiers visually with an accessible
   full-value title or disclosure. Provide a copy button only if it can be
   implemented without unnecessary complexity.

6. EVIDENCE

   On wide screens use a right-side evidence rail labelled:

   “Evidence · <count> sources”

   Keep it collapsed or summarized initially. Opening evidence must reveal:

   - Evidence ID
   - Human-readable kind
   - Confidence
   - Locator
   - Retrieval command
   - Excerpt

   Translate labels for display only:
   - checkpoint_metadata → Checkpoint metadata
   - checkpoint_transcript → Checkpoint transcript
   - git_diff → Git diff
   - graph_impact → Graph impact
   - graph_warning → Graph limitation

   Preserve original raw values in the ReviewBundle.

   On smaller screens, evidence becomes an in-flow drawer below the active card.

7. CONTINUE SAFELY

   Present continuation as one compact secondary panel directly after the
   active review.

   Heading: “Continue safely”
   Explain that these are evidence-backed next steps.
   Preserve the exact continuation claim and source link.

8. STICKY VOICE DOCK

   Keep voice controls visible at the bottom.

   Primary controls:
   - Previous
   - Play/Pause
   - Next

   Secondary controls:
   - Repeat
   - Stop
   - Read evidence
   - Speech rate

   Display:
   - “Step X of 4”
   - current card name
   - concise “What will be spoken” preview
   - “Local voice ready” or “Local voice unavailable”

   Do not show “180 local browser voices are available.” The exact count has no
   user value.

   Never auto-play, auto-advance or begin listening.
   Only use voices where voice.localService === true.
   Preserve text fallback when no local voice exists.

   Selecting Previous/Next changes the active card but must not automatically
   start speech.

9. DEVELOPMENT FIXTURE

   Do not show “Use included fixture (development only)” as a prominent
   production action.

   Keep fixture functionality available for tests and development:
   - automatically show a small “Development fixture” indicator when
     ?mode=fixture is present;
   - offer fixture recovery only in the unavailable/error state;
   - do not display it in the normal successful review path.

MICROINTERACTIONS

Use restrained 160–200ms transitions for:

- navigation selection
- button hover/pressed state
- evidence disclosure
- context disclosure
- active-card change
- voice playing/paused state

Prefer background, border and opacity transitions. Avoid large movement,
parallax, bouncing, continuous animation and layout shifts.

Implement:

- active navigation background: var(--entire-accent-soft)
- active indicator: var(--entire-accent)
- hover background: var(--entire-surface-muted)
- pressed state without dramatic scaling
- 3px accessible violet focus ring with sufficient offset
- play button state change between Play and Pause
- subtle progress movement between steps

Under prefers-reduced-motion: reduce, disable all non-essential transitions and
animations.

- minimum WCAG AA contrast
- zoom at 200%
- high readability and generous line height
- no color-only information
- no auto-focus
- no auto-scroll
- no auto-advance

- Focused and Detailed reading modes
